# Analyzer Refactoring

## Цель

Цель рефакторинга — превратить текущий Analyzer из анализатора АЧХ в универсальную систему анализа аудиосигнала.

Analyzer должен перестать быть частью EQ Matching и стать независимым компонентом, способным описывать любые свойства аудио. В дальнейшем эти данные смогут использоваться для подбора параметров любой цепочки обработки: эквалайзера, компрессора, сатуратора и любых других эффектов.

Главный принцип — Analyzer ничего не знает о DSP, параметрах эффектов и алгоритме оптимизации. Его единственная задача — максимально точно описать звучание сигнала.

---

# Общая архитектура

```
Audio
    ↓
Window Processing
    ↓
Feature Extractors
    ↓
Statistics
    ↓
Feature Vector
```

Полученный Feature Vector используется другими компонентами системы.

```
Reference
        ↓
   Analyzer
        ↓
 Feature Vector

Candidate
        ↓
   Analyzer
        ↓
 Feature Vector

        ↓
       Loss
        ↓
   Optimizer
```

Таким образом Analyzer является полностью независимым модулем.

---

# Анализ сигнала

Анализ производится потоково.

Сигнал разбивается на небольшие окна (примерно 20–50 мс), после чего каждое окно проходит через все зарегистрированные Feature Extractor'ы.

Важно понимать, что отдельное окно практически ничего не говорит о характере звука. Поэтому конечный результат строится не на отдельных измерениях, а на статистике большого количества окон.

Analyzer должен описывать поведение сигнала за несколько секунд, а не его мгновенное состояние.

---

# Feature Extractor

Каждый Feature представляет собой полностью независимый модуль.

Он отвечает только за анализ одного свойства сигнала.

Например:

- FFT
- RMS
- Peak
- Crest Factor
- Spectral Centroid
- Spectral Flux
- Spectral Flatness
- Loudness
- Envelope
- Attack
- Transient Energy

Каждый Feature имеет собственное внутреннее состояние и самостоятельно обрабатывает поступающие окна.

Никакой Feature не должен зависеть от других.

---

# Статистика

Feature не возвращает значение одного окна.

Его задача — накопить статистику за весь анализируемый фрагмент.

Например могут вычисляться:

- среднее значение
- дисперсия
- минимумы
- максимумы
- процентили

Для спектральных данных статистика собирается отдельно для каждого FFT-бина.

Таким образом результатом анализа становится не измерение, а описание поведения сигнала.

---

# Частотные диапазоны

Большинство Feature должны уметь работать как со всем спектром, так и с отдельными диапазонами.

Например:

- 20–80 Hz
- 80–250 Hz
- 250–700 Hz
- 700–2 kHz
- 2–6 kHz
- 6–20 kHz

Диапазон является параметром Feature, а не отдельным типом класса.

---

# Feature Vector

После завершения анализа результаты всех Feature объединяются в единый Feature Vector.

Он представляет собой компактное описание звучания анализируемого сигнала.

Этот объект должен использоваться для:

- сравнения сигналов;
- оптимизации;
- визуализации;
- отладки;
- сохранения профилей;
- последующего анализа.

Analyzer не вычисляет итоговую ошибку между двумя сигналами.

Он лишь строит их описание.

---

# Loss

Сравнение двух сигналов выполняется отдельным компонентом.

На вход он получает два Feature Vector.

```
Reference Features

Candidate Features

↓

Loss
```

Каждый Feature имеет собственный вес.

Например:

```
FFT              × 1.0
RMS              × 0.6
Transient        × 0.8
Spectral Flux    × 0.4
```

Это позволит создавать различные режимы анализа.

Например:

- EQ Matching
- Compressor Matching
- Saturation Matching

без изменения самого Analyzer.

Текущая реализация захватывает один синхронный фрагмент pre-DSP current и
reference. Каждый кандидат прогоняется по этому фрагменту offline через общую
DSP-цепь и тот же Feature Pipeline. Начало фрагмента используется как warm-up
устройств и не входит в loss. Loss рассчитывается по всем глобальным и
полосовым метрикам. В поиск входят активные EQ-фильтры выбранного банка,
входной и выходной gain, compressor и saturator. В Host записывается только
один финальный результат.

---

# Основные принципы

Analyzer должен быть:

- полностью потоковым;
- независимым от оптимизатора;
- независимым от DSP;
- расширяемым;
- модульным;
- не хранить исходный аудиосигнал;
- хранить только необходимое состояние и накопленную статистику.

Добавление нового Feature должно требовать только регистрации нового модуля без изменения существующей архитектуры.

---

# Дальнейшее развитие

В дальнейшем поверх Analyzer могут быть построены:

- универсальный Loss;
- универсальный Optimizer;
- автоматический подбор параметров любой цепочки эффектов;
- профилирование инструментов;
- сравнение различных алгоритмов обработки;
- визуализация Feature Vector.

Таким образом Analyzer становится фундаментальным компонентом всей системы Consolidator и больше не зависит от конкретного типа аудиообработки.
