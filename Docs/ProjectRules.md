# Consolidator Native — правила разработки

## Общий принцип

## Статус проекта

Проект находится на стадии активного прототипирования. Обратная совместимость,
fallback-пути, миграционные адаптеры, compatibility aliases и параллельные legacy API
запрещены, если пользователь явно не запросил их. При изменении архитектуры все
вызывающие стороны переводятся на новую модель, а старый API удаляется напрямую.

Код должен быть современным, модульным, объектным и легко читаемым.

Главная цель — не просто заставить систему работать, а сохранить понятную архитектуру,
в которой каждый компонент имеет ограниченную ответственность и находится в предсказуемом месте.

Запрещено превращать файлы, классы и функции в бесконечные простыни кода.
Если код становится трудно читать целиком, его необходимо разделить на отдельные методы,
структуры, классы, компоненты или файлы.

---

## Reference: Native.Old

`Native.Old/` (бывшая `Native/`) — **предыдущая C++ кодовая база**.
Это **источник контекста**: мы должны воспроизвести её функциональность в новой архитектуре
`Consolidator.Native/`, отрефакторив и избавившись от технического долга.
Нельзя линковаться против неё. Нельзя копировать файлы напрямую.

## Именование (naming conventions)

| Элемент | Стиль | Пример |
|---|---|---|
| Классы, структуры | **PascalCase** | `ConsolidatorInstance`, `ParameterSmoother` |
| Методы (включая static) | **PascalCase** | `Process()`, `GetRuntimeState()` |
| Пространства имён | **PascalCase** | `consolidator::core`, `consolidator::dsp` |
| Переменные (локальные) | **camelCase** | `frameCount`, `sampleRate` |
| Поля классов | **camelCase_** (trailing underscore) | `instanceId_`, `buffer_` |
| Параметры функций | **camelCase** | `mainInput`, `referenceInput` |
| Константы | **PascalCase** или **kPrefix** | `kChannelCount`, `DefaultSampleRate` |
| Макросы | **UPPER_SNAKE_CASE** | `CONSOLIDATOR_LOG`, `CONSOLIDATOR_DEV` |
| Файлы | **PascalCase** | `ConsolidatorInstance.h`, `Log.cpp` |

Имена должны объяснять назначение сущности. Никаких абстрактных/бессмысленных названий.
Имена должны быть согласованы по всему проекту.

## 1. Структура проекта

Код организован по функциональным областям. Внутри каждой области файлы группируются
по конкретной ответственности.

Папки должны отражать архитектуру и назначение кода, а не случайную историю его появления.

```text
Source/Core/         — domain model, instance, state, registry, routing, commands
Source/Dsp/          — audio processors, parameter smoothing, buffers
Source/Analysis/     — FFT, curve accumulation, metrics
Source/Optimization/ — fitting solvers, search strategies
Source/Max/          — Min external entrypoint, message adapters
Tests/               — unit and integration tests (Core, Dsp)
```

Всё выше `Source/Max` должно компилироваться без Max или Min заголовков.

---

## 2. Размер файлов

Один файл = одна основная сущность или один тесно связанный набор небольших сущностей.

Не создавать чрезмерно большие файлы, содержащие множество несвязанных задач одновременно.
Если файл становится большим — определить отдельные ответственности и вынести их.
Разделение должно соответствовать смыслу, а не формальным ограничениям.

### Command handlers

Каждый конкретный command handler должен находиться в отдельном исходном файле.
Имя файла включает владельца и scope handler-а:

- `ConsolidatorInstance.CommandSubmission.cpp` — приём и постановка команды instance;
- `InstanceCoordinator.CommandSubmission.cpp` — приём и постановка команды координатора;
- `InstanceCoordinator.WorkerLoop.cpp` — рабочий цикл coordinator и обработка очереди;
- `CommandRouter.CommandHandler.cpp` — dispatch command variant;
- `CommandRouter.WriteCommandHandler.cpp` — обработка write-команды;
- `CommandRouter.ReadCommandHandler.cpp` — обработка read-команды.

Один `.cpp` не должен содержать несколько независимых handlers. Основные `.cpp`
владельцев содержат lifecycle, state access и orchestration, но не реализацию
command handlers. Для каждого нового command scope сначала создаётся явный
handler-файл, затем он подключается к dispatch-цепочке. Вспомогательные шаги,
которые принадлежат только одному handler scope — например write plan,
topology write, delivery и refresh ответа — должны находиться рядом с этим
handler-ом, а не разноситься по отдельным техническим `.cpp`. Отдельный файл
для таких шагов нужен только при наличии самостоятельной ответственности или
реального переиспользования.

## 3. Размер функций

Функция выполняет одну понятную операцию.

Не писать длинные методы с последовательным сценарием из множества шагов —
такой сценарий должен быть разделён на именованные шаги.
Название метода должно объяснять намерение.

Выносить метод следует когда он:
- представляет отдельный шаг;
- скрывает детали;
- повторно используется;
- улучшает читаемость;
- упрощает тестирование.

Не создавать бессмысленные обёртки, не добавляющие ясности.

---

## 4. Ответственность классов

Каждый класс имеет одну основную ответственность.
Избегать названий, скрывающих реальную ответственность.
Крупные объекты не должны превращаться в контейнер всей системы — они должны
состоять из отдельных компонентов и координировать их, а не реализовывать всю логику.

---

## 5. Поля классов

Не создавать длинные списки разрозненных полей.
Связанные данные объединять в структуры.

Структура должна представлять осмысленное понятие. Объединять данные, которые:
- изменяются вместе;
- передаются вместе;
- описывают одну сущность;
- имеют общий жизненный цикл;
- логически принадлежат одному уровню.

Не создавать абстрактные контейнеры без ясного смысла.

---

## 6. Параметры функций

Связанные аргументы должны быть объединены в структуру.
Структура должна выражать отдельное понятие предметной области, а не быть формальной упаковкой.

---

## 7. Заголовочные и исходные файлы

Заголовок описывает публичный контракт. Реализация отделена от объявления.
В заголовках — только необходимые элементы интерфейса.
Не перегружать заголовки реализацией. Минимизировать зависимости.

---

## 8. Уровни абстракции

Одна функция работает на одном уровне абстракции.
Не смешивать высокоуровневую логику с низкоуровневыми деталями.
Детали реализации — в соответствующих компонентах, а не в управляющих слоях.

Абстракции вводить только когда они действительно необходимы:
- скрывают сложность;
- используются в нескольких местах;
- позволяют замену реализации;
- упрощают публичный интерфейс;
- могут тестироваться отдельно.

---

## 9. Современный C++

- C++20, RAII everywhere.
- `std::unique_ptr`, `std::array`, `std::span`.
- Без ручного управления памятью где не требуется.
- Без сырых указателей для владения.
- Strong types для domain IDs (`InstanceId`, `GroupId`, `BankId`).
- Разные сущности → разные типы (защита от случайных ошибок).
- Без string-based dispatch.
- Нет god objects.

---

## 10. Комментарии

Комментарии объясняют причины, а не повторяют код.
Если код требует большого количества комментариев — улучшить его структуру.
Не хранить устаревший закомментированный код.

---

## 11. Вспомогательные функции

Не создавать общий набор случайных утилит.
Вспомогательные функции — рядом с областью, к которой относятся.
Общие функции допустимы только при реальной необходимости.

---

## 12. Ошибки и проверки

Ошибки должны обнаруживаться как можно раньше.
Строгие типы и явные проверки. Не скрывать и не игнорировать ошибки.

---

## 13. Дублирование

Не дублировать одну и ту же логику в разных местах.
При повторении — определить смысл и вынести в общее место.

---

## 14. Зависимости между слоями (hard rule)

```text
Max → Core
Core → Dsp
Core → Analysis
Core → Optimization
```

Запрещено:
- `Core → Max`
- `Dsp → Max`
- `Analysis → Max`
- `Optimization → Max`

Нижние слои не зависят от верхних. Каждый слой знает только то, что ему необходимо.

---

## 15. Изменение существующего кода

При добавлении логики нельзя просто расширять существующие большие сущности.
Сначала определить:
- принадлежность ответственности;
- необходимость новой структуры;
- влияние на архитектуру;
- возможность изоляции;
- тестируемость.

Изменения должны улучшать структуру, а не ухудшать.

---

## 16. Real-time правила

- Никаких аллокаций в audio thread.
- Никаких mutex/lock/wait в DSP.
- Никакого I/O, логирования, строкового форматирования в audio callback.
- Все буферы preallocated до первого `Process()`.
- State updates — double-buffer или atomic snapshot patterns.
- FFT/analysis вне audio thread.

---

## 17. Logging

- Макрос `CONSOLIDATOR_LOG(category, message)` из `Core/Logging/Log.h`.
- Доступен **только** при `-DCONSOLIDATOR_DEV=ON`.
- В production сборках — no-op.
- Логи пишутся в `Logs/` (автосоздание в runtime).
- Никогда не вызывать из audio thread.
- Уместные применения:
  - жизненный цикл instance (create, destroy, reset);
  - buffer resize / reallocation;
  - configuration changes;
  - offline analysis progress;
  - ошибки/предупреждения вне DSP.

---

## 18. Форматирование (style consistency)

## C++ Code Formatting Rules

При форматировании C++-кода необходимо улучшать только читаемость и визуальную структуру. Не изменять архитектуру, поведение, алгоритмы, публичный API или семантику кода без отдельного запроса.

### Общие правила

* Открывающую фигурную скобку размещать на новой строке.
* Всегда использовать фигурные скобки для `if`, `for`, `while`, `switch` и других управляющих конструкций, даже если тело состоит из одной строки.
* Не размещать несколько инструкций или объявлений функций в одной строке.
* Между логическими блоками оставлять одну пустую строку.
* Не добавлять избыточные пустые строки.
* Закрытие namespace оформлять комментарием:

### Порядок include

Сначала подключать заголовок текущего файла, затем стандартную библиотеку, затем заголовки проекта:

```cpp
#include "Dsp/Processors/Gain/Gain.h"

#include <algorithm>
#include <cmath>
#include <cstddef>
#include <cstdint>

#include "Dsp/Parameters/ParameterHelper.h"
```

Между этими группами оставлять пустую строку.

Добавлять прямой include стандартного заголовка, если тип из него используется непосредственно в файле. Например:

```cpp
#include <cstdint>
```

для `std::uint8_t`.

### Сигнатуры функций

Короткую сигнатуру оставлять в одной строке:

```cpp
void Gain::RecalculateRuntime()
```

Длинную сигнатуру переносить по одному аргументу на строку:

```cpp
void Equalizer::Process(
    const double* input,
    double* output,
    std::size_t frameCount,
    std::size_t channelCount)
```

То же правило применять к объявлениям в заголовочных файлах:

```cpp
void Process(
    const double* input,
    double* output,
    std::size_t frameCount,
    std::size_t channelCount) override;
```

Не переносить сигнатуру без необходимости, если она хорошо помещается в одну строку.

### Конструкторы и списки инициализации

Для короткого конструктора допустимо:

```cpp
explicit Gain(DeviceId deviceId) noexcept
    : deviceId_(deviceId)
{
}
```

Если список инициализации длинный, каждый сложный элемент размещать отдельно:

```cpp
TiltFilter::TiltFilter(
    FilterId FilterId,
    double pivotHz)
    : Filter(
          DeviceId::Equalizer,
          detail::ElementKind::EqFilter,
          detail::ToIndex(FilterId)),
      lowShelf_(FilterId, pivotHz),
      highShelf_(FilterId, pivotHz)
{
}
```

### Условия и ранние возвраты

Условия оформлять развёрнуто:

```cpp
if (filter != nullptr)
{
    filters_.push_back(std::move(filter));
}
```

Для раннего возврата использовать отдельный блок:

```cpp
if (change.address.GetDeviceId() != deviceId_)
{
    return;
}
```

Составные условия переносить так, чтобы операторы были визуально заметны:

```cpp
if (filter->GetElementKind() == elementKind &&
    filter->GetElementIndex() == elementIndex)
{
    return filter.get();
}
```

### Switch

Каждый `case` оформлять отдельным блоком. Не размещать условие, вызов и `break` в одной строке:

```cpp
switch (change.address.GetParameterId())
{
case ParameterId::Gain:
    if (const auto* value = TryGetValue<float>(change))
    {
        runtime_.gainDb = *value;
        RecalculateRuntime();
    }
    break;

case ParameterId::Bypass:
    if (const auto* value = TryGetValue<bool>(change))
    {
        runtime_.bypass = *value;
    }
    break;

default:
    break;
}
```

При чтении значения через `TryGetValue` использовать `const auto*`, если значение не изменяется.

### Локальные переменные

Использовать понятные имена вместо однобуквенных сокращений:

```cpp
const double amplitude = GainDbToAmplitude(parameters_.gainDb);
const double cosine = std::cos(omega);
const double inverseA0 = 1.0 / a0;
```

Вместо:

```cpp
const double amp = ...;
const double cosO = ...;
const double invA0 = ...;
```

Исключение составляют общепринятые математические обозначения, такие как `q`, `a0`, `b0`, `z1`, `z2`.

Не переименовывать публичные поля, параметры или API только ради форматирования.

### Выражения и вычисления

Простое выражение оставлять в одной строке:

```cpp
const auto sampleCount = frameCount * channelCount;
```

Длинное вычисление переносить по логическим частям:

```cpp
runtime_.outputGainLinear =
    std::pow(
        10.0,
        static_cast<double>(runtime_.outputDb) / 20.0);
```

Для длинных арифметических выражений разбивать формулу так, чтобы структура была видна:

```cpp
coefficients.b0 =
    gain *
    ((gain + 1.0) -
     (gain - 1.0) * cosine +
     gainRootTerm) *
    inverseA0;
```

### Временные значения

Если значение используется несколько раз или улучшает читаемость, сохранять его в локальную переменную:

```cpp
const double cosine = std::cos(omega);
```

В обработке аудиобуфера использовать понятные промежуточные значения:

```cpp
const double detectorInput = CalculateLinkedDetectorInput(input + frameOffset, channelCount);
const double inputLevelDb = MeasureLevelDb(detectorInput);
```

Не создавать временные переменные, если они только усложняют простой код.

### Классы

Соблюдать порядок секций:

1. `public`
2. `protected`
3. `private`

Между крупными группами методов оставлять пустую строку.

Сначала размещать конструкторы и основные методы, затем getters, затем внутренние методы и поля.

Пример:

```cpp
class Gain final : public IDspDevice
{
public:
    explicit Gain(DeviceId deviceId) noexcept;

    void Process(
        const double* input,
        double* output,
        std::size_t frameCount,
        std::size_t channelCount) override;

    void ApplyParameterChange(const ParameterChange& change) override;

    [[nodiscard]] DeviceId GetDeviceId() const noexcept override
    {
        return deviceId_;
    }

private:
    void RecalculateRuntime();

    DeviceId deviceId_;
    GainRuntimeState runtime_;
};
```

### Inline-методы

Короткие getters допускается оставлять inline, но тело оформлять на нескольких строках:

```cpp
[[nodiscard]] const GainRuntimeState& GetRuntimeState() const noexcept
{
    return runtime_;
}
```

Не оформлять их в одну строку:

```cpp
[[nodiscard]] const GainRuntimeState& GetRuntimeState() const noexcept { return runtime_; }
```

Простой составной возврат также переносить по логическим частям:

```cpp
[[nodiscard]] bool IsNeutral() const noexcept override
{
    return runtime_.bypass ||
           runtime_.linearGain == 1.0;
}
```

### Константы

Каждую константу объявлять отдельно:

```cpp
static constexpr float kMinimumAttackMs = 0.01f;
static constexpr float kMaximumAttackMs = 2000.0f;
```

Не объединять несколько констант в одном объявлении:

```cpp
static constexpr float kMinimumAttackMs = 0.01f,
                       kMaximumAttackMs = 2000.0f;
```

Связанные минимальные и максимальные значения группировать рядом.

### Указатели

При проверке указателей использовать явное сравнение с `nullptr`, когда это улучшает читаемость:

```cpp
if (filter != nullptr)
{
    // ...
}
```

В простом guard-условии допустима непосредственная проверка, но стиль должен быть единообразным в пределах файла.

### Атрибуты

Использовать `[[nodiscard]]` для методов, возвращаемое значение которых не должно игнорироваться:

```cpp
[[nodiscard]] Filter* GetFilter(std::size_t index) noexcept;
```

Не добавлять атрибуты, если это может изменить существующие требования сборки или вызвать нежелательные предупреждения, без отдельного запроса.

---
## Критерий качества

Код считается качественным, если:
- его легко найти по структуре;
- назначение понятно по именам;
- он не перегружен деталями;
- он разделён по смыслу;
- его можно понимать по частям;
- изменения не требуют знания всей системы.

---

## Главное правило

Предпочитать структурированный и понятный код, даже если он немного длиннее.
Код должен читаться как система взаимодействующих компонентов, а не как набор случайных инструкций.

## Документация перед коммитом

Перед созданием коммита необходимо проверить документацию, затронутую изменением.
Изменения архитектуры, правил, структуры проекта и workflow должны сопровождаться
обновлением соответствующей документации в том же коммите.
